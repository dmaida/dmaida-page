# Docker Compose Patterns for Self-Hosted Services

When I started self-hosting, every service was its own `docker run` command buried in my shell history. It worked until it didn't — a reboot, a typo, a container I couldn't remember how I'd started. Then I moved everything to Docker Compose, and the whole thing got calmer.

But Compose only gets you so far on its own. The difference between a homelab that quietly runs for months and one you're forever babysitting comes down to a handful of patterns. These are the ones I reach for in every `compose.yaml` I write.

---

## Start With a Sane Skeleton

Here's the shape every service file follows. Modern Compose doesn't need the `version:` key anymore — drop it.

```yaml
# compose.yaml
services:
  app:
    image: ghcr.io/example/app:1.2.3
    container_name: app
    restart: unless-stopped
    env_file: .env
    volumes:
      - ./data:/data
    ports:
      - "8080:8080"
```

That's a complete, working service. Everything below is about making it *robust* — surviving reboots, failing loudly, and not leaking secrets.

---

## Pin Your Image Tags

The single most common self-hosting footgun is `image: app:latest`. It means "whatever I happened to pull last," which makes your setup unreproducible and your 2 a.m. breakages mysterious.

```yaml
# Bad — you can never reproduce what's actually running
image: ghcr.io/example/app:latest

# Good — explicit, reproducible, intentional upgrades
image: ghcr.io/example/app:1.2.3
```

Pin to a specific version and bump it deliberately. When an upgrade breaks something, you'll know exactly what changed and can roll back to the previous tag.

## Restart Policies That Match Reality

`restart: unless-stopped` is the right default for almost every self-hosted service. It brings the container back after a crash or a host reboot — but respects you if you *intentionally* stopped it.

```yaml
services:
  app:
    restart: unless-stopped
```

The four options, and when each makes sense:

| Policy | Behavior |
|---|---|
| `no` | Never restart (the default — rarely what you want) |
| `always` | Always restart, even if you stopped it manually |
| `unless-stopped` | Restart on crash/reboot, but stay down if you stopped it |
| `on-failure` | Restart only on a non-zero exit — good for one-shot jobs |

For long-running services, use `unless-stopped`. For a batch task that should run once and stop, `on-failure` is the better fit.

## Healthchecks: Teach Compose What "Up" Means

A container being *running* doesn't mean the app inside is *ready*. A healthcheck closes that gap — Compose marks the container healthy only when the app actually responds.

```yaml
services:
  app:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s
```

`start_period` is the underrated field: it gives a slow-booting app (databases, anything with migrations) a grace window before failed checks start counting against it.

If the image doesn't ship `curl`, use whatever it *does* have — `wget`, the app's own CLI, or a simple TCP check:

```yaml
    # No curl in the image? wget works too
    test: ["CMD", "wget", "--spider", "-q", "http://localhost:8080/health"]
```

## depends_on With Conditions

`depends_on` on its own only waits for a container to *start*, not to be *ready*. Combined with a healthcheck, you can make a service wait until its database is genuinely accepting connections.

```yaml
services:
  app:
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
```

Now `app` won't even start until `db` reports healthy. This eliminates the classic "app crashes on boot because the database wasn't ready yet" race — no more restart loops on every reboot.

## Keep Secrets Out of the Compose File

Never hard-code passwords and API keys into `compose.yaml` — it's the file you most want to commit to git. Push them into a `.env` file that lives next to the Compose file and is *git-ignored*.

```yaml
# compose.yaml — references variables, contains no secrets
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

```bash
# .env — git-ignored, holds the actual values
POSTGRES_PASSWORD=super-secret-value
```

```bash
# .gitignore
.env
```

Compose loads `.env` automatically. Commit a `.env.example` with empty placeholders so future-you (or anyone cloning the repo) knows which variables are required.

For higher-stakes secrets, Compose also supports the `secrets:` block, which mounts values as files in the container instead of exposing them as environment variables:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

## Named Volumes vs. Bind Mounts

Two ways to persist data, and the choice matters more than people expect.

```yaml
services:
  app:
    volumes:
      # Bind mount — host path you can see, back up, and edit directly
      - ./config:/config
      # Named volume — Docker-managed, better for databases
      - app-data:/data

volumes:
  app-data:
```

**Bind mounts** (`./config:/config`) are great for config you want to read and edit on the host. **Named volumes** (`app-data:/data`) are managed by Docker and generally better for database storage — fewer permission headaches and better performance on some platforms. I use bind mounts for config, named volumes for data.

## A Shared Network for Your Reverse Proxy

Once you're running more than a couple of services, you'll want a reverse proxy (Caddy, Traefik, nginx) in front of them so everything's reachable by hostname over HTTPS. The pattern: an *external* shared network that every service joins.

```bash
# Create the shared network once
docker network create proxy
```

```yaml
# Each service joins it and labels itself for the proxy
services:
  app:
    networks:
      - proxy
    labels:
      caddy: app.example.com
      caddy.reverse_proxy: "{{upstreams 8080}}"

networks:
  proxy:
    external: true
```

With `external: true`, the network is shared across multiple Compose projects — your proxy in one stack can route to services defined in completely separate `compose.yaml` files. Note that once a service is reachable through the proxy, you usually want to *remove* its host `ports:` mapping so it's only accessible via the proxy, not directly.

## Reusable Config With YAML Anchors

When ten services all want the same logging config or restart policy, anchors (`&`) and aliases (`*`) keep you from repeating yourself.

```yaml
x-common: &common
  restart: unless-stopped
  env_file: .env
  networks:
    - proxy

services:
  app:
    <<: *common
    image: ghcr.io/example/app:1.2.3

  worker:
    <<: *common
    image: ghcr.io/example/worker:1.2.3

networks:
  proxy:
    external: true
```

The `x-` prefix marks a top-level extension field that Compose ignores as a service but lets you reference. `<<: *common` merges those shared keys into each service. Change the policy once, and it applies everywhere.

## The Day-to-Day Commands

```bash
# Start everything in the background
docker compose up -d

# Apply changes after editing compose.yaml (recreates only what changed)
docker compose up -d

# Tail logs for one service
docker compose logs -f app

# Pull newer images, then recreate
docker compose pull && docker compose up -d

# Check status, including health
docker compose ps

# Stop and remove containers (volumes are kept)
docker compose down
```

Note `docker compose` (a space, the v2 plugin) rather than the old `docker-compose` binary. And `down` does **not** delete named volumes unless you add `-v` — so your data is safe by default.

## Quick Reference

| Pattern | Why it matters |
|---|---|
| Pin image tags | Reproducible, intentional upgrades |
| `restart: unless-stopped` | Survives reboots, respects manual stops |
| Healthchecks | Compose knows when the app is *actually* ready |
| `depends_on: service_healthy` | No more boot-order race conditions |
| `.env` + `.gitignore` | Secrets never hit git |
| Named volumes for data | Fewer permission and performance headaches |
| External `proxy` network | One reverse proxy fronts every stack |
| YAML anchors | Shared config without repetition |

---

## Worth It?

These patterns aren't fancy — they're the boring 20% that gets you 80% of a reliable homelab. Pin your tags so upgrades are deliberate, add healthchecks so failures are visible, keep secrets out of git, and put everything behind one reverse proxy. Do that, and your services survive reboots, fail loudly instead of silently, and stop being a source of low-grade dread.

The best compliment a homelab can earn is being forgotten about. These patterns are how you get there.
